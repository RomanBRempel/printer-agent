# Задание для RD Control: удалённая настройка агента — `settings_request` / `settings` / `settings_update`

Направление: `printer-agent` → RD Control. Формат и правила — в
[docs/agent-collaboration.md](../agent-collaboration.md).

Контракт-владелец: [docs/contracts/agent-hub-v1.md](../contracts/agent-hub-v1.md)
в этом репозитории, разделы `settings`, `settings_request`, `settings_update`.
Ломающих изменений нет, `PROTOCOL_VERSION` остаётся `1`: добавляются три типа
сообщений, существующие формы не тронуты. Агент со стороны провода готов
(`0.1.0a19`), включая приём того, чего хаб ещё не шлёт.

---

## Зачем

Настройки агента правились только на самой машине — через десктопное приложение
или переносом файла настроек. Практический предел этого виден в сегодняшнем
разборе: чтобы завести на площадке новый принтер или поменять принтеру IP,
нужен человек за тем конкретным компьютером.

Теперь состав принтеров, учётки, интервалы и настройки обновлений правятся из
хаба по той же сессии, которой уже идёт телеметрия. Новых портов и входящих
соединений у агента не появилось — модель «только исходящие» сохранена.

## Что появилось на проводе

**Хаб → агент, `settings_request`** — пустой payload. Ответ — `settings`.
`command_id` нет, `command_result` не будет: это запрос состояния, как
`inventory_request`.

**Агент → хаб, `settings`** — то, чем агент сейчас настроен:

```json
{
  "location_key": "loc-001",
  "agent_version": "0.1.0a19",
  "request_msg_id": "req-1",
  "settings": {
    "telemetry_interval_s": 5,
    "heartbeat_interval_s": 15,
    "command_reconnect_backoff_s": { "min": 1, "max": 60 },
    "outbox": { "max_events": 5000 },
    "print_files": { "max_age_h": 72, "max_total_mb": 2048 },
    "updates": { "feed_url": "https://…", "auto_update": true, "check_on_startup": true, "check_interval_h": 6 },
    "printers": [
      { "key": "a1-mini-sancho", "brand": "bambu", "host": "10.13.0.126",
        "credentials": { "access_code": "__redacted__", "serial": "0309…" } }
    ]
  },
  "readonly": {
    "hub_url": "https://…/api/printers/agent",
    "outbox": { "database_path": "C:\\ProgramData\\printer-agent\\outbox.sqlite3" }
  }
}
```

**Хаб → агент, `settings_update`** — набор изменений, `command_id` обязателен:

```json
{ "command_id": "cmd-9", "settings": { "telemetry_interval_s": 10 } }
```

Ответ — обычный `command_result`, у которого **`printer_key` пустая строка**:
команда про агента, а не про принтер. Поле присутствует и пустое, а не
отсутствует, чтобы его можно было читать безусловно.

## Четыре правила, на которых это держится

Каждое из них ломается молча, если сделать наоборот.

**1. `__redacted__` означает «оставь как есть».** Агент никогда не отдаёт
секреты наверх: `access_code`, API-ключи и пароли приезжают в `settings` этой
строкой. Хаб, который нарисовал форму из `settings` и сохранил её целиком,
пришлёт маркер обратно — и агент обязан понять это как «не трогай». Так и
сделано. Опасность в другом: **не показывайте маркер оператору как значение
поля**. Он увидит `__redacted__` в поле «код доступа», сотрёт его, впишет
пустоту — и это уже не маркер, а очистка.

Различайте три состояния поля в форме: секрет задан (пришёл маркер), не задан
(поля нет вовсе) и «оператор хочет убрать» (отправить `null`). Пустая строка —
это «оставь как есть», а не «убери».

**2. `printers` заменяет список целиком.** Другого способа сказать «этого
принтера больше нет» на проводе нет. Отсюда: чтобы поменять один принтер, надо
прислать **весь** список, иначе остальные будут удалены. Чтобы не трогать состав
— не присылать ключ `printers` вообще. Пустой массив удаляет все принтеры, и
агент это сделает.

Практически это значит, что форму редактирования принтера надо строить от
свежего `settings`, а не от того, что хаб запомнил при `hello`.

**3. Четыре поля агент откажется менять.** `hub_url`, `agent_token`,
`location_key`, `outbox.database_path`. Они называют сессию и открытую базу —
то, что работающий агент не может поменять, не разобрав себя, — и ошибка в них
оставляет агента без канала, которым его можно было бы починить. Они вернутся в
`rejected`, а не будут молча выброшены. **Не показывайте их редактируемыми**:
`hub_url` и путь к базе приезжают в блоке `readonly` именно для показа.

Если правка состояла только из таких полей, ответ будет `failed`, а не `done`:
«принято» на изменение, которого не произошло — худший из возможных ответов.

**4. `done` означает «принято», а не «уже действует».** Агент пишет `agent.yaml`
и отвечает. Изменение подхватывает обычный перечитыватель конфига в течение
одного `telemetry_interval_s`: он пересобирает адаптеры для добавленных,
удалённых и изменённых принтеров и **присылает `inventory` сам**. То есть
подтверждение того, что правка подействовала, — это `inventory`, а не
`command_result`.

Из этого следует то, чего не обойти: **пока хаб не принимает `inventory`, он не
узнает результат удалённой правки.** Это тот самый отказ
`unknown_message_type`, описанный в
[rd-control-inventory-request.md](rd-control-inventory-request.md) и снова
замеченный в поле 18.08
([rd-control-field-report-2026-08-18.md](rd-control-field-report-2026-08-18.md)).
Удалённую настройку без него делать можно, но она будет работать вслепую.

## Что в `response` у `command_result`

```json
{
  "applied": ["telemetry_interval_s", "printers[3]"],
  "kept_local": ["printers.a1-mini-sancho.credentials.access_code"],
  "rejected": ["hub_url"],
  "missing": ["printers.jekson-p1s.credentials.access_code"],
  "restart_required": false
}
```

Всё — имена полей, не значения: секрет не попадёт ни в ответ, ни в журнал.

- `applied` — записано в файл.
- `kept_local` — хаб прислал маркер или ничего, осталось значение агента.
- `rejected` — отказано; показать, не повторять.
- `missing` — не задано нигде, а адаптеру нужно. Bambu без кода доступа не
  подключится и не примет файл: принтер будет `offline`, пока код не появится.
  **Это стоит показывать в карточке принтера** — иначе оператор увидит новый
  принтер в парке и не поймёт, почему он не отвечает.
- `restart_required` — сейчас всегда `false`.

`status` — `done`, если что-то применилось; `failed`, если нет: либо
объединённый конфиг не проходит валидацию (тогда **на диск не записано ничего**,
а `error_text` перечисляет ошибки), либо в правке были одни отказанные поля.

## Что сделать на стороне хаба

1. **Принимать `settings`** и уметь показать его как форму — с учётом правила 1
   про три состояния секрета.
2. **Слать `settings_request`**, когда оператор открывает эту форму. Периодически
   не нужно: настройки меняются редко, а ответ всегда актуален на момент запроса.
3. **Слать `settings_update`** с `command_id` и обрабатывать `command_result` с
   пустым `printer_key`. Показывать `rejected` и `missing`, а не только статус.
4. **Считать молчание нормой.** Агент старой версии не знает эти типы, логирует
   неизвестный тип и не отвечает. Хаб обязан по таймауту сказать «этот агент
   старее» и не помечать его сбойным — тогда рассылать запрос можно всем сразу,
   не сверяясь с версиями.
5. **Хранить секреты принтеров как секреты.** Раз хаб теперь умеет их присылать,
   он стал их хранилищем: шифрование на хранении, отсутствие в журналах, никакого
   возврата в ответах API оператору.
6. **Принять `inventory`** — без него правка уйдёт в пустоту, см. правило 4.

## Порядок выкатки

Правило 3 из [agent-collaboration.md](../agent-collaboration.md): принимающая
сторона первой. По всем трём сообщениям принимающая сторона по одному разу и та,
и другая, поэтому порядок такой:

| Сообщение | Кто принимает | Кто выкатывается первым |
|---|---|---|
| `settings_request` | агент | агент (уже в коде) |
| `settings` | хаб | **хаб** |
| `settings_update` | агент | агент (уже в коде) |
| `command_result` с пустым `printer_key` | хаб | **хаб** |

То есть хаб может начинать в любой момент: агент готов и молчит, пока его не
спросят. Проверьте только, что валидатор `command_result` на стороне хаба не
требует непустой `printer_key` — иначе ответ на `settings_update` будет отвергнут
как некорректный.

## Приёмка

На живом соединении:

1. Хаб шлёт `settings_request`, агент отвечает `settings`; в ответе нет ни одного
   настоящего секрета, а заданные видны как `__redacted__`.
2. Оператор в форме хаба меняет `telemetry_interval_s` и сохраняет: приходит
   `command_result` со `status: done` и полем в `applied`, `agent.yaml` на машине
   изменился.
3. Оператор добавляет Bambu с кодом доступа: в течение одного цикла телеметрии
   приходит `inventory` с новым принтером, принтер выходит на связь и его можно
   закрепить.
4. Оператор сохраняет форму, ничего не поменяв: коды доступа на месте, принтеры
   не отвалились.
5. Хаб пробует прислать `hub_url`: `status: failed`, `hub_url` в `rejected`,
   агент остался на прежнем хабе.

## Чего я не менял и почему

- Ничего в репозитории RD Control — по правилу 4 раздела 3
  [agent-collaboration.md](../agent-collaboration.md).
- Не сделал `settings` рассылаемым по своей инициативе, как `inventory`.
  Настройки меняются потому, что их кто-то поменял, и этот кто-то уже знает.
- Не дал хабу менять `hub_url` и токен, хотя это выглядит удобным: удалённая
  правка канала связи — единственная правка, ошибка в которой чинится только
  выездом на площадку.
