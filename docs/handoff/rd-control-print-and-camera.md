## 2. Что сделано сейчас

**`file_offer` исполняется.** Скачивание по `url` с тем же `Authorization: Bearer`,
потоком во временный файл (не в память), проверка `sha256` **и** `size_bytes`,
атомарный `os.replace` в кеш под именем `file_ref`, затем передача на принтер.
Несовпадение суммы — `failed`, файл удаляется, **на принтер не уходит ничего**.
Кеш свой, с ретенцией по возрасту и по суммарному размеру (`print_files` в
конфиге, по умолчанию 72 ч / 2 ГБ).

Коды отказа разобраны как в задании: `401`/`403`/`404`/`409` — `failed` без
повтора и с человекочитаемой причиной в `error_text`; `503` — повтор с backoff в
пределах `expires_at`. Дополнительно: если `X-Print-File-Sha256` расходится с
`sha256` команды, файл не вычитывается вовсе — хаб отдаёт не ту ревизию.

**Идемпотентность.** Повтор того же `command_id` возвращает сохранённый результат
из outbox, без второй загрузки и без второй выгрузки на принтер. Проверено
тестом.

**`start_print`.** Использует `remote_name` для адресации на принтере,
`file_ref` — для проверки, что файл у агента есть. Файла нет — `failed`, `file_ref`
в `error_text`; **сам за файлом агент не идёт**.

**Камера.** `camera_request` запускает один цикл на принтер: кадр у адаптера раз в
`interval_s`, POST на `upload_url` с тем же токеном, `Content-Type` определяется
по байтам кадра, `X-Captured-At` проставляется. Ответ хаба авторитетнее
`camera_stop`: `404`/`409` гасят съёмку немедленно, `400`/`413`/`500` её не
прерывают. Кадр больше `max_bytes` не отправляется вовсе — 413 был бы платой за
заведомо лишний трафик. Кадры нигде не копятся: ни в outbox, ни в памяти.

**`state.ams.slots[]`** отправляется в снапшоте — для Bambu, из отчёта принтера.
Форма — по контракту (`index`, `material`, `color`, `remaining_pct`). Пустой слот
приезжает как слот без материала, а не пропадает: «слота нет» и «слот пуст» — для
сверки материала разные ответы.

**`file_offer` исполняется рядом с приёмным циклом.** Передача сотни мегабайт
занимает минуты, и inline она заблокировала бы всё остальное — heartbeat, `ack`,
следующую команду. Практическое следствие для хаба ниже, §3.

## 3. Что важно знать хабу

1. **`command_result` по `file_offer` может прийти через минуты.** Ждать его
   надо дольше, чем ответ на `pause`; срок доставки команды должен покрывать
   время передачи файла, иначе хаб закроет её как `expired` в момент, когда файл
   уже едет на принтер. Обрыв связи в этот момент безопасен: результат лежит в
   outbox агента, и повторная выдача той же команды вернёт его без второй печати.

2. **Флаги `capabilities` у Bambu стали `false`.** `upload` и `camera` были
   подняты авансом, при нереализованных FTPS и RTSP. Теперь они отражают факт —
   у Bambu и Creality обе функции закрыты, у Moonraker `upload` открыт всегда, а
   `camera` — когда снимок реально отвечает. Это не регресс: кнопка исчезла
   ровно там, где она вела к отказу. Ждём от хаба формулировку «принтер не умеет
   принимать файлы» вместо ошибки.

3. **`camera` у Moonraker может приехать `false` в `hello` и `true` следом в
   телеметрии.** Адрес снимка ищется при первом подключении к принтеру, а `hello`
   уходит раньше. Хаб уже читает `capabilities` из снапшота — просьба не кешировать
   их исключительно из `hello`.

4. **`expires_at` в `camera_request` агент трактует как ОКНО МОЛЧАНИЯ, а не как
   момент.** Отсчёт продлевается любым ответом хаба на кадр, поэтому зритель,
   смотрящий десять минут, поток не теряет, а оборванная связь гасит съёмку через
   это окно. Если хаб ожидает жёсткой остановки ровно в `expires_at` — скажите,
   поменяем: сегодня остановка идёт через `409`, как и описано в вашем документе.

5. **Дефект хаба, о котором вы сами написали:** `state.ams` отбрасывается
   фильтром «медленной» части состояния, и сверка материала всегда даёт «не
   проверено». Агент данные шлёт — правка на вашей стороне.

6. **Отдельного факта «печать закончилась» агент не шлёт** и слать не будет:
   исход выводится из снапшота, где `status` авторитетнее блока `job`. Это
   зафиксировано в контракте (раздел Snapshot semantics), чтобы правило
   `eb60902` не осталось знанием одной стороны.

## 4. Чего ещё нет

- **Загрузка и старт у Bambu и Creality.** Первым сделан Moonraker — там
  протокол описан и предсказуем. Для Creality путь загрузки надо снимать с
  прошивки (у части моделей HTTP на `:80`, у части только вендорный канал); до
  этого `capabilities.upload` остаётся `false`.
- **Камера у Bambu (RTSP) и Creality (MJPEG).** Тот же порядок: сначала кадр
  реально читается, потом поднимается флаг.
- **Приёмка §5 на реальном принтере.** Она требует живого стенда: у этого
  репозитория нет ни хаба, ни БД, ни принтера в CI. Проверки уровня «форма
  сообщений, порядок шагов, поведение при обрыве» закрыты тестами; проверки
  уровня «деталь уехала и напечаталась» — за вами и владельцем парка.
