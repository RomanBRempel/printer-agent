# Задание для RD Control: запрос состава принтеров — `inventory_request` / `inventory`

Направление: `printer-agent` → RD Control. Формат и правила — в
[docs/agent-collaboration.md](../agent-collaboration.md).

Контракт-владелец: [docs/contracts/agent-hub-v1.md](../contracts/agent-hub-v1.md)
в этом репозитории. Ниже — только то, что нужно сделать **на стороне хаба**.
Ломающих изменений нет, `PROTOCOL_VERSION` остаётся `1`: добавляются два новых
типа сообщений, существующие формы не тронуты.

---

## Зачем

Состав принтеров агента приезжал на хаб ровно один раз — в `hello`, при
подключении сессии. Спросить его заново было нечем: единственный способ получить
свежий список — уронить сессию и дождаться переподключения.

Это било по живому сценарию. На площадке добавили принтер, в списке «закрепить за
агентом» его нет, и по внешним признакам не отличить три разных причины: агент не
перечитал конфиг, хаб не получил `hello`, или принтер не закреплён. Хаб при этом
отклоняет телеметрию по незакреплённому ключу (`error` с
`code: "printer_not_found"`) — то есть данные идут, но пропадают, а причина видна
только в логе агента.

Теперь хаб может спросить состав в любой момент.

## Что появилось на проводе

**Хаб → агент, `inventory_request`** — пустой payload:

```json
{ "v": 1, "type": "inventory_request", "msg_id": "req-1", "ts": "2026-08-15T09:00:00Z", "payload": {} }
```

**Агент → хаб, `inventory`:**

```json
{
  "v": 1,
  "type": "inventory",
  "msg_id": "ans-1",
  "ts": "2026-08-15T09:00:00Z",
  "payload": {
    "location_key": "loc-001",
    "agent_version": "0.1.0a9",
    "request_msg_id": "req-1",
    "printers": [
      {
        "printer_key": "printer-1",
        "brand": "moonraker",
        "capabilities": { "pause": true, "resume": true, "cancel": true, "upload": true, "camera": false, "ams": false, "cfs": false }
      }
    ]
  }
}
```

`printers[]` — **тот же массив, что в `hello`**, поле в поле. У агента его строит
одна функция для обоих сообщений, и это закреплено тестом; у хаба он должен
читаться одним парсером, а не двумя похожими.

`request_msg_id` **отсутствует**, когда агент шлёт `inventory` по своей инициативе
— он делает это, заметив, что его `agent.yaml` изменился. То есть принтер,
добавленный на площадке, доезжает до хаба без перезапуска службы: агент замечает
правку в течение одного цикла телеметрии, перестраивает адаптеры и присылает новый
состав сам.

## Что сделать

1. **Уметь отправлять `inventory_request`.** Разумные моменты: оператор открыл
   экран закрепления принтеров за агентом, сработала сверка состава, админ нажал
   «обновить список». Периодически слать не нужно — состав меняется редко.

2. **Сопоставлять ответ по `request_msg_id`.** Он равен `msg_id` конверта
   запроса. Собственный `msg_id` у ответа свой, как у любого сообщения.

3. **Считать отсутствие ответа нормой, а не ошибкой.** Агент старой версии не
   знает этот тип, логирует его как неизвестный и молчит. Хаб обязан по таймауту
   откатиться к составу из `hello` и не помечать агента сбойным. Это же снимает
   вопрос порядка выкатки: слать запрос можно всем агентам сразу.

4. **Не ждать `command_result`.** У `inventory_request` нет `command_id`: он не
   действие над принтером, а запрос состояния. Ответ всегда `inventory`.

5. **Не путать состав с доступностью.** В списке — принтеры, на которые агент
   **сконфигурирован**. Недоступный принтер из состава не исчезает, его состояние
   приезжает телеметрией как `offline`. Удалять принтер из парка по признаку
   «нет в сети» нельзя — только по отсутствию в `inventory`.

6. **Принимать `inventory` без `request_msg_id` в любой момент сессии.** Это не
   ошибка протокола, а инициатива агента после правки конфига. Такой список
   заменяет состав целиком: принтера, которого в нём нет, у этого агента больше
   нет. Практически это и есть путь, которым новый принтер попадает в хаб без
   перезапуска службы, так что обработчик этого сообщения важнее обработчика
   ответа на запрос.

## Порядок выкатки

Правило 3 из [agent-collaboration.md](../agent-collaboration.md) — принимающая
сторона первой — здесь работает в обе стороны, и по одному из двух сообщений
первым идёт **хаб**:

| Сообщение | Кто принимает | Кто выкатывается первым |
|---|---|---|
| `inventory_request` | агент | агент (уже в коде; старые версии молча игнорируют) |
| `inventory` без запроса | хаб | **хаб** |

То есть агент с этими изменениями нельзя раскатывать по площадкам, пока хаб не
умеет принять `inventory`, пришедший сам по себе. Как минимум — не считать
неизвестное сообщение ошибкой сессии.

Второй пункт того же порядка: если хаб сейчас отвечает `error` с
`printer_not_found` на телеметрию незакреплённого принтера, это стоит убрать
**до** обновления агентов — иначе события будут не копиться до закрепления, а
уничтожаться (см. раздел ниже).

## Приёмка

На живом соединении: хаб шлёт `inventory_request`, агент отвечает `inventory` с
`request_msg_id`, равным `msg_id` запроса, и составом, совпадающим с тем, что
приехало в `hello` этой же сессии. Оператор дописывает принтер в `agent.yaml` —
в течение одного цикла телеметрии приходит `inventory` без `request_msg_id` с
новым принтером, и он доступен для закрепления в парке. Агент версии без
поддержки типа не отвечает на запрос, и хаб продолжает работать на составе из
`hello`.

## Изменение поведения агента по сообщению `error`

Раньше агент на `error` только писал строку в лог: отклонённое событие оставалось
в outbox и переотправлялось, поэтому на площадке с незакреплённым принтером рос
счётчик pending. Теперь агент делает то, для чего в `error` существует поле
`msg_id`, — **снимает событие с отправки навсегда**.

Следствие, которое стоит учесть на стороне хаба: `error` уместен для сообщения,
которое хаб не примет **никогда**, и неуместен для того, которое он не может
принять **пока** — принтер ещё не закреплён, хранилище временно недоступно. Во
втором случае правильнее промолчать: событие останется в outbox, и агент повторит
его сам, когда связь или состояние на хабе изменятся. Если сейчас
`printer_not_found` отправляется на телеметрию незакреплённого принтера, эти
события будут потеряны безвозвратно, и после закрепления история не подтянется.
