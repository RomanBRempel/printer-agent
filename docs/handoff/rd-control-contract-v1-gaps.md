# Задание для RD Control: приём agent-hub v1 после ревизии контракта

Направление: `printer-agent` → RD Control. Формат и правила — в
[docs/agent-collaboration.md](../agent-collaboration.md).

Контракт-владелец: [docs/contracts/agent-hub-v1.md](../contracts/agent-hub-v1.md)
в этом репозитории. Ниже — только то, что нужно сделать **на стороне хаба**.
Ломающих изменений нет, `PROTOCOL_VERSION` остаётся `1`: всё аддитивно либо
фиксирует то, что уже происходит на проводе.

Хаб — принимающая сторона для всех сообщений `agent → hub`, поэтому пункты 3-5
выкатываются **раньше**, чем агенты в поле начнут на них опираться. Пункты 1-2 —
наоборот, сообщения `hub → agent`: агент уже готов их принять, ждём хаб.

---

## 1. `hello_reject` обязан нести `code` — иначе агент останавливается навсегда

**Что мешает.** Агент теперь различает временный отказ и окончательный. Логика:
`code == "temporarily_unavailable"` → обычный reconnect с backoff; **любой другой
код, неизвестный код и отсутствие поля `code` → сессия прекращается, агент не
переподключается**.

**Где в вашем коде.** `services/printers/protocol.py` — место, где формируется
отказ на `hello`.

**Следствие для пользователя.** Если хаб отвергает агента по временной причине
(рестарт, миграция БД, переполнение), но без `code`, весь парк агентов этой
локации замолчит до ручного перезапуска службы на каждой точке. Обратный случай
тоже плох: `auth_rejected`, помеченный как временный, даёт бесконечный долбёж
хаба заведомо неверным токеном.

**Что сделать.** Отдавать `{"code": ..., "reason": ...}`, где `code` —
одно из: `protocol_unsupported`, `auth_rejected`, `location_unknown`,
`temporarily_unavailable`. `reason` — человеческий текст, агент его только
логирует и никогда не парсит.

**Приёмка.** Агент, получивший `temporarily_unavailable`, продолжает
переподключаться; агент, получивший `auth_rejected`, пишет причину в лог и
останавливается, не повторяя `hello`.

---

## 2. `command_id` в `file_offer`, `camera_request`, `camera_stop`

**Что мешает.** Эти три сообщения хаба отвечаются обычным `command_result`, но
`command_id` в них до сих пор не отправлялся. `command_result` без `command_id`
хабу нечего сопоставить, поэтому агент такое сообщение **молча дропает** с
записью в лог.

**Где в вашем коде.** Формирование исходящих `file_offer` / `camera_request` /
`camera_stop` в `services/printers/protocol.py`.

**Следствие для пользователя.** Оператор жмёт «показать камеру» или отправляет
файл — в интерфейсе задача висит без ответа до таймаута, при том что агент
сообщение получил.

**Что сделать.** Добавить `command_id` (и `printer_key`) во все три. Агент
сейчас отвечает на них `status: "unsupported"` — это ожидаемо, функции ещё нет;
важно, чтобы ответ был **сопоставим**, а не потерян.

---

## 3. `event.kind` — четыре значения, а не одно

Хаб должен принимать `snapshot`, `status_changed`, `job_changed`,
`error_changed`. Агент шлёт **по одному событию на каждый kind**, то есть одна
смена состояния может дать три события подряд с одинаковым снапшотом. `snapshot`
— первое наблюдение принтера после старта агента, сравнивать не с чем.

Неизвестный `kind` нельзя ронять в 500: событие лежит в durable outbox и будет
переслано бесконечно.

---

## 4. Аддитивные поля, которые уже идут на проводе

- `command_result.printer_key` — отправляется, в контракте раньше не значился.
- `telemetry.snapshots[].ts` — время снятия снапшота на стороне агента.
- **Отсутствующее значение опускается, а не шлётся как `null`.** Снапшот без
  ошибки несёт `error: {}`; неизвестные температуры просто отсутствуют.
  Проверка `is None` на стороне хаба не сработает — нужно трактовать
  отсутствующий ключ и пустой объект одинаково.

---

## 5. `error` — зафиксировать форму, которую вы уже шлёте

Агент обрабатывает сообщение `error` (`{code, message, msg_id}`) как отказ по
одному сообщению без разрыва сессии, и в контракт оно теперь внесено. Просьба
подтвердить, что `msg_id` в нём — это `msg_id` **отвергнутого конверта**: агент
опирается на это, чтобы перестать пересылать событие из outbox.

## Приёмка стыка

На живом соединении, одним прогоном:

1. агент подключается, хаб отвечает `hello_ack`; в логе агента есть
   `hub accepted the agent`;
2. хаб шлёт `command` с `action: "pause"` → приходит `command_result` с тем же
   `command_id`; повтор той же команды возвращает **тот же** результат, не
   выполняя действие второй раз;
3. хаб шлёт `camera_request` с `command_id` → приходит `command_result`
   `unsupported` с этим `command_id`;
4. принтер выключают → в хаб приходят события `status_changed` (и `error_changed`,
   если адаптер отдал ошибку), каждое подтверждается `ack`, после чего outbox
   агента пуст;
5. хаб отвечает `hello_reject` с `temporarily_unavailable` → агент
   переподключается; с `auth_rejected` → агент останавливается с причиной в логе.

Пока этот прогон не сделан, задача не закрыта ни у одной из сторон.
