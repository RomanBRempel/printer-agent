# Задание для RD Control: обновление агента из хаба — `update_request` и блок `update`

Направление: `printer-agent` → RD Control. Формат и правила — в
[docs/agent-collaboration.md](../agent-collaboration.md).

Контракт-владелец: [docs/contracts/agent-hub-v1.md](../contracts/agent-hub-v1.md)
в этом репозитории, разделы `update_request`, `hello`, `inventory`. Ломающих
изменений нет, `PROTOCOL_VERSION` остаётся `1`: добавляется один тип сообщения
и один необязательный блок в двух существующих. Агент готов с **`0.1.0a33`**.

---

## Зачем

Обновление доезжало до площадки само, но по расписанию: проверка при старте
службы и раз в `updates.check_interval_h`. На машине, которая работает неделями,
это означало сутки ожидания между выпуском исправления и его приездом — а
исправление, как правило, выпускается потому, что на площадке что-то встало.

Теперь то же самое делается по нажатию: хаб просит агента поставить обновление
той же исходящей сессией, которой идёт телеметрия. Новых портов у агента не
появилось.

## Что появилось на проводе

**Хаб → агент, `update_request`** — команда про самого агента, не про принтер.

```json
{ "command_id": "cmd-12", "target_version": "0.1.0a33" }
```

`target_version` необязателен. Если он задан, а лента предлагает другую версию,
команда отказывает и ничего не ставит: на парке, где оператор ждёт одно
конкретное число, «примерно то же самое» — это не то же самое.

**Агент → хаб, `command_result`** с пустым `printer_key`.

```json
{
  "scheduled": true,
  "current_version": "0.1.0a32",
  "latest_version": "0.1.0a33",
  "waiting_for_idle": false,
  "restarts_itself": true
}
```

**Агент → хаб, блок `update`** — в `hello` и в `inventory`, рядом с
`agent_version`:

```json
{ "current_version": "0.1.0a33", "latest_version": "0.1.0a33", "update_available": false }
```

## Три вещи, которые не видны из формы

**Ответ говорит «запланировано», а не «обновился».** Установка ждёт момента,
когда перезапуском ничего не теряется — не идёт передача файла, не открыта
камера, — и перезапускает процесс. Ответ, посланный после перезапуска, до хаба
бы не дошёл. Подтверждение — `hello` перезапустившегося агента с новым
`agent_version`. Ровно та же развязка, что у `settings_update`: команда говорит
«принято», а следующее сообщение говорит «подействовало». Идущая печать
ожиданием не считается — её принтер доводит сам, пока агент перезапускается.

**Блок `update` отсутствует, пока лента не проверялась.** «Не знаем» и
«обновлений нет» — разные утверждения, и показать второе вместо первого значит
объявить агента актуальным, ничего об этом не зная. Ключа нет — показывайте
«не проверялось», а не «последняя версия».

**Агент старше `0.1.0a33` не отвечает вовсе.** Незнакомый тип сообщения он
пишет в журнал и роняет — отказа, который можно показать человеку, не приходит,
и команда висит в состоянии «отправлена» бесконечно. Это уже наблюдалось на
площадке 26.08.2026: команду отправили агенту `0.1.0a32`, ответа не было и быть
не могло.

## Что просим сделать на стороне хаба

1. **Закрыть кнопку по версии.** `agent_version` приезжает в `hello` и в каждом
   `inventory`. Ниже `0.1.0a33` — кнопка неактивна и подписана требуемой
   версией. Отправлять команду, единственный возможный исход которой — тишина,
   не нужно.
2. **Дать команде срок.** Даже у поддерживающего агента ответ может не прийти —
   сессия рвётся. Строка в списке команд не должна оставаться «отправлена»
   навсегда; по истечении срока — «ответа нет», а не вечное ожидание.
3. **Показывать доступную версию из блока `update`**, а отсутствие блока — как
   «не проверялось».
4. **Не ждать `command_result` как подтверждения обновления.** Признак того, что
   версия встала, — новый `agent_version` в следующем `hello`. При
   `restarts_itself: false` (запуск из консоли) нового `hello` не будет вовсе:
   пакет поставлен, но старый код работает, пока его не перезапустят руками.

## Первый агент на парке

Этой командой парк на `0.1.0a33` не поднять — она в нём и появилась. Первый
переход делается тем, что уже есть: перезапуском службы (`check_on_startup`
проверяет ленту при старте) либо ожиданием очередной проверки. Дальше каждая
следующая версия ставится кнопкой.

Отдельно: правка `updates.check_interval_h` через `settings_update` **не**
приближает ближайшую проверку. Интервал читается один раз при запуске задачи
обновления, и новая величина вступит в силу только после перезапуска.
